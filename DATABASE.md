# Database Specification

This document describes the SQLite schema generated by `scripts/initialize_db.py` (via `bballInitializeDB`). The schema is defined only as string constants in that file — there is no migration tooling.

Conventions for the per-table tables below:

- **Column**: column name as it appears in `CREATE TABLE`.
- **Type**: declared SQLite type affinity.
- **Nullable**: whether the column permits `NULL`. `NOT NULL` means it does not.
- **Default**: `DEFAULT` expression, or `-` if none.
- **Check**: `CHECK` constraint, or `-` if none.
- **Key**: `PRIMARY KEY` / `FOREIGN KEY ... REFERENCES table(column)` / `UNIQUE`, or `-`.

Notes:

- SQLite does not enforce foreign keys unless `PRAGMA foreign_keys = ON` is issued on the connection; the schema declares them but enforcement is opt-in.
- Several `FOREIGN KEY` clauses reference table names that do not exist in the schema (`referees`, `executives`, `coaches` — the actual tables are `referee_info`, `executive_info`, `coach_info`). Those references are no-ops.
- In `game_info`, the `In_Season_Tournament` and `Play_In` CHECK constraints are written against the `Playoffs` column rather than their own column.

## Table: `team_info`

One row per team per season. For the NBA backend this is guaranteed by the season-qualified team hrefs in `id_cache` (`/team/<teamId>/<season>`); a franchise in a different season is a distinct href and gets a distinct `Team_ID`. The NBA backend fills `Wins`/`Losses`/`League_Ranking`/`Playoff_Appearance`/`Season` from stats.nba.com standings (season-accurate), not the live team page. ESPN matches this: its team hrefs are `/espn/team/<teamId>/<season>`, and `Wins`/`Losses`/`League_Ranking`/`Playoff_Appearance` come from the season's standings endpoint, with `Playoff_Appearance` derived as `0 < playoffSeed <= 8`.

|---|---|---|---|---|---|
| Name | TEXT | yes | - | - | - |

| Losses | INTEGER | no | - | Losses >= 0 | - |

## Table: `id_cache`

Mapping of provider-specific hrefs to the stable integer IDs used as primary keys throughout the schema. This table is what makes every `get_*` engine call idempotent: the same href from the same source always maps to the same ID, so re-running a scrape over an existing DB reuses IDs instead of duplicating rows.

| Column | Type | Nullable | Default | Check | Key |
|---|---|---|---|---|---|
| basketball_reference | TEXT | yes | - | - | - |
| nba | TEXT | yes | - | - | - |
| espn | TEXT | yes | - | - | - |
| value | INTEGER | no | - | - | - |
| type | TEXT | yes | - | - | - |

Table-level constraint: `UNIQUE (basketball_reference, nba, espn, type)`.

**How it is written.** Every `get_*` method on the engine (`get_player_info`, `get_team_info`, `get_game_info`, `get_season_info`, `get_referee_info`, `get_executive_info`, `get_coach_info`) assigns a stable integer ID to an href and immediately persists the pair via `engine.update_id_cache(href, ID, cache, location)` (`abstract.py`). That method writes one row: the href goes into the column matching the engine's `_source` (`"basketball reference"` → `basketball_reference`, `"nba"` → `nba`, `"espn"` → `espn`), `value` holds the assigned ID, and `type` holds which info kind the ID belongs to (`player_info`, `team_info`, `season_info`, `game_info`, `referee_info`, `executive_info`, `coach_info`, `rankings`, `game_data`).

**How it is read.** On startup the engine's `get_id_cache()` runs `SELECT <source>, value FROM id_cache WHERE type = '<location>'` for each info type and loads the pairs into in-memory dicts (`player_id_cache`, `team_id_cache`, etc.). `get_*` then short-circuits: `if href in cache` → return the existing object/ID without re-fetching or re-inserting. Only hrefs not already cached get a new ID (seeded from `*_max_id`, the max cached value for that type).

**What `value` means per `type`.**
- `*_info` types: the integer primary key for that entity (e.g. the `Team_ID` referenced by `team_info`, `game_info.Home_Team_ID`/`Away_Team_ID`, `team_games.Team_ID`/`Opponent_ID`, `player_games.Player_ID`, etc.). IDs are sequential per type and are **not** unique across types — the `UNIQUE` constraint is per (source, href, type).
- `season_info`: `value` is the season integer itself (the `Season` primary key), not an arbitrary sequence.
- `rankings`: `value` is the team's league ranking for that season.
- `game_data`: `value = 1` is a "scraped" marker, not a real ID; it keeps `get_game_data` from re-scraping a game's boxscore on re-runs.

**Why hrefs carry a season qualifier.** The href is the identity key, so its *granularity* determines how many IDs an entity gets. Basketball-Reference hrefs are already season-scoped (`/teams/BOS/2009.html`). NBA team hrefs are built as `/team/<teamId>/<season>` (e.g. `/team/1610612738/2024`), so the same franchise in a different season is a distinct href → distinct `Team_ID` → the "one row per team per season" invariant in `team_info`. ESPN team hrefs are season-qualified (`/espn/team/<id>/<season>`) because `team_info` carries a `Season` column; ESPN **player** hrefs are deliberately season-less (`/espn/athlete/<id>`) because `player_info` has no `Season` column — a season in a player href would mint one `Player_ID` per season, which `player_games.Player_ID` then FKs to and silently breaks cross-season aggregation. ESPN coach hrefs are deliberately *not* season-qualified (`/espn/coach/<personId>`) because the `coach_info` table has no `Season` column, so a coach is one career row; their Wins/Losses are career-to-date rather than season-accurate. ESPN referee hrefs are name slugs (`/espn/referee/<name-slug>`), so two officials sharing a name would alias to one ID. Game/player/referee hrefs are otherwise not season-qualified (a player is one row across seasons; a game is inherently unique). Changing an href scheme therefore orphans the old rows in `id_cache` and the tables that reference them; re-scraping under a new scheme starts fresh IDs.
